# USER WISHLIST

Quelle: Samuel im HAI-Dialog

## 1. Pre-Registration vor dem nächsten Run
Schreib vor dem Lauf in eine Datei (z.B. `experiment/preregistration_2026-05-10.md`):
- exakte Hypothese mit Effektgröße: „baseline_6line erzielt auf Tasks T1..Tn ≥10 pp höhere task_success-Rate als negative_control_karpathy40."
- Falsifikationskriterium: „Wenn der Unterschied <10 pp oder negativ ist, gilt die Hypothese in diesem Scope als nicht gestützt."
- Stopping-Rule: „Genau N Runs pro Cell, danach wird ausgewertet, egal was rauskommt."
- Sobald du das nach dem Schauen auf Daten formulierst, ist es kein Test mehr, sondern Storytelling.

## 2. n hochziehen, sonst ist alles Rauschen
3 Successes auf 98 Runs = Boden-Effekt, da diskriminiert nichts. Zwei Optionen:
- Task-Auswahl im diskriminierbaren Mittelfeld: pilotiere kurz, behalte nur Tasks mit Pilot-Success-Rate zwischen ~20–80%. Tasks bei 0% oder 100% liefern null Information.
- Mehr Runs pro Cell: mindestens 10 pro (Task × Condition), realistisch eher 20+. Ja, das kostet — aber alles darunter ist statistisch nicht trennbar von Zufall.

## 3. Confounds zumachen
- gleicher Model-Snapshot, gleiche temp, gleicher seed-Pool über alle Conditions
- blindes Judging: der Judge (oder du) sieht Diff + Testergebnis, nicht welche Policy gelaufen ist
- random task order, nicht „erst alle baseline, dann alle karpathy“ — sonst confoundest du Tageszeit/Modell-Drift

## 4. Scope ehrlich klein halten
Die einzige saubere Aussage am Ende ist:
„In genau diesem Harness, mit Modell M, auf Task-Sample T, von Judge J bewertet, mit n=k pro Cell, war Effekt E (mit CI [a,b])."

Das ist keine Schwäche — das ist die einzige Form, in der der Befund Popper-fest steht. Generalisierungs-Sprache („.md X macht Agenten besser") ist dann automatisch ausgeschlossen.
